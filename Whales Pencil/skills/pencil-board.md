# 神笔鲸良 —— 桌面画板

桌面最上层铺着一块透明画板（`pencil` 工具）。用户和你共用它，两个人同时在上面说话。

## 画之前：确认窗口活着

`pencil draw` 只是把笔画写进 `scene.json`。**真正把它显示出来的是桌面窗口**——一个独立的 PowerShell 进程。窗口没在跑的时候，`draw` 照样返回成功，但屏幕上什么都没有。

插件已经处理了这个：每次 `draw` 之前会检查 `window.txt` 里的 pid，进程死了就自动用指令把窗口拉起来，然后才返回。

所以：

- **返回里的 `onScreen` 是 `true`** → 笔画真的在屏幕上了
- **`onScreen` 是 `false`** → 窗口起不来（极少见），这时不要假装画好了，直接告诉用户

遇到 `onScreen: false` 的处理：

```
pencil { action: "overlay", overlay: "start" }
```

再不行就如实报告，别自己编一个「已经画好了」。

### 旧状态可能骗人

`overlay: "running"` 是宿主内存里的状态，**不等于窗口活着**。窗口可能在你上次操作之后崩了、被我重启插件时换掉了，或者启动到一半就死了。这就是为什么 pid 文件才是权威：它由窗口自己在加载完成时写入。

插件在启动时也会做一次同样的检查——**发现进程没活着就先启动**，不用等第一次画。

## 红的就是用户

**画板上的红色笔画和红色文字，全部是用户画的。** 用户的铅笔只有红色，没有任何别的颜色，所以他手里没有第二支可选。

这意味着红色不是装饰，是**用户的声音**：

| 你看到的 | 用户的意思 |
|---|---|
| 一个红圈 | 「这个」——他把话题限定在这块区域 |
| 一根红箭头 | 「那个方向」/「往那里」 |
| 一段红字 | 他打的问题或回答 |
| 随手一条红线 | 划重点，或者只是试笔 |

**不要把这些当成背景，也不要无视。** 用户用画板是因为他懒得多打字，或者光靠说说不清。

## 你也要画回去

这是双向的。用户在屏幕上指了东西，你**只在对话里回复是不够的**——他的眼睛可能在别处，也可能根本没切过来看聊天窗。

规则：**用户画了什么，你就画回去。**

```
1. pencil scene          先读：他的笔画 points、他的文字 texts（含坐标）
2. 想清楚他在指哪块区域
3. pencil draw           在他指的地方写：一段 text、一个框、一根箭头
```

### 画在哪里

- **圈了某个控件** → 就在那个控件旁边写答案，别写到屏幕角落
- **打了问题** → 就在问题下面接着写回答
- **画了箭头** → 箭头指的终点就是他要你看的地方

### 坐标系：申报 `view`，不要自己换算

坐标最终是**桌面物理像素**，原点在左上角。默认 `unit: "screen"`；用 `unit: "window"` 则是屏幕百分比。

**你看到的图，尺寸可能和真实桌面不一样。** 视觉模型收到的图会被降采样，你的 `pwsh` 进程可能是 DPI 不感知的（125% 缩放下只看到 1536×864，而屏幕真实是 1920×1080）。

所以规则是：

> **你按哪个尺寸量，就把那个尺寸填进 `view`。**

```json
pencil { action: "draw", view: { "w": 1536, "h": 864 }, items: [...] }
```

工具会按 `真实尺寸 / view` 的比例，把你给的所有坐标、尺寸、字号自动换算过去。**你不该自己乘除。**

| 情况 | 怎么做 |
|---|---|
| 在截图上量的坐标 | `view: {w: <截图实际宽度>, h: <截图实际高度>}` |
| 已经是真实桌面像素 | 省略 `view` |
| 不确定 | 先 `pencil scene`，看返回的 `screen` |

`pencil scene` 和每次绘制结果都带真实尺寸：

```json
{ "screen": { "w": 1920, "h": 1080, "x": 0, "y": 0 } }
```

**看返回里的 `rescaled` 字段**，它会告诉你有没有换算、比例多少：

```
rescaled — view 1536x864 mapped to 1920x1080 (x1.2500, y1.2500)
```

`landed at` 是你画的东西**真实落点**。画完先看这两个字段对不对，再决定要不要继续。

⚠️ **`view` 填得离谱会被拒绝**（比例超出 0.25–4 倍），此时坐标原样使用并给出警告——你不会在不知情的情况下被拉歪。

⚠️ **历史故障**：曾经有 agent 拿 1536 的坐标直接画到 1920 的画板上，整体缩到 0.8 倍；发现偏了之后编了一个「画板被压缩」的错误理论，越修越远。**记住：偏了先看 `screen` 和 `rescaled`，别编理论。**

### 用什么颜色

**你的笔迹永远不用红色。** 红是留给用户的，撞色会让两个人分不清谁是谁。

常用：

| 用途 | 颜色 |
|---|---|
| 一般说明、答案 | `#00E5FF` 青 |
| 强调、警告 | `#FFD400` 琥珀 |
| 确认、对 | `#7CFFB2` 绿 |
| 正文小字 | `#FFFFFF` 白 |

## 他也能擦你画的

用户的右键是橡皮擦，**不区分谁的笔迹**。所以他擦掉你的标注不是 bug，是在说「这个不用了」。

你也有 `erase`，按 `ids` 或 `rects` 擦。**但你不能一键清除**——清空整块画板只有用户能做，因为那会推翻他的工作。

## 一点实操经验

- **画面会累积。** 用过一次就 `erase` 掉自己的旧标注，别让屏幕越堆越乱。
- **字别太小。** 用户是在看屏幕，不是在读文档。`size` 至少 16，重点用 20 以上。
- **别画满屏。** 只标用户指的地方。整屏铺满的框会挡住他要看的东西。
- **他圈了什么，先读坐标再动笔。** `pencil scene` 里就有他的笔画和文字，直接读。
- **大致位置就够了。** 圈东西时用眼睛估个大概，直接画；误差几十像素完全没关系。
  不要为了「更精确」写脚本、查注册表、做像素分析——那是绕远路，用户看着你写文件只会更困惑。
  需要看被挡住的桌面时，用钛合金鱼眼的 `eye { action: "desktop" }`，别自己写截图脚本。

## 擦除：用 id，别用大矩形

**这是最容易出错的地方，务必读。**

`erase` 有两种参数，后果完全不同：

| 参数 | 行为 |
|---|---|
| `ids: ["a12-0", "a12-3"]` | **精确**删除这几个图元 |
| `rects: [{x,y,w,h}]` | 删除**任何与矩形相交**的图元 |

`rects` 是"扫一片"，**会把那片里所有东西一起带走**，包括你刚画好的、以及你不想动的内容。用大矩形擦一小块，结果往往是整个标注被清空，然后你不得不重画——重画时坐标又记不清，于是越画越偏。

**正确顺序：**

```
1. pencil draw   → 返回里带 drawn:[id...] 和 bounds:[{x,y,w,h}...]
2. 要改哪一块，就用 drawn 里对应的 id
3. pencil erase { ids: ["那个id"] }
4. pencil draw 新版本
```

`draw` 的返回一定看这两个字段：

```json
{ "drawn": ["a15-0", "a15-1"], "drawnCount": 2, "dropped": 0,
  "bounds": [{"x":534,"y":136,"w":135,"h":148}, ...] }
```

- `drawn` —— 这批图元的真实 id，下次擦除直接引用
- `bounds` —— 服务端算出的实际包围盒，用它核对位置是否如你所愿
- `dropped` —— 大于 0 说明画板满了（上限 4000），有图元被挤掉

`erase` 的返回也告诉你擦掉了什么：

```json
{ "erasedCount": 6, "erased": ["a12-0","a12-1",...] }
```

**`erasedCount` 超过你预期，就是矩形开大了。** 这时不要继续擦，先 `pencil scene` 看清楚还剩什么。

## 呼唤

托盘上的「呼唤 agent」会给你送来一张当前屏幕，同时告诉你去读画板。

收到呼唤时的正确顺序：

1. 看图，看用户在哪个界面
2. `pencil scene` 读他的笔画和文字——**这是他真正在说的内容**
3. 如果他用红圈/红字提了问题，**在画板上画回去**
4. 对话里也说明一句，但别只靠对话
