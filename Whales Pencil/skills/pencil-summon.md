# 呼唤 —— 用户按了托盘的门铃

用户没法随时打断你说话，所以托盘上有一个「呼唤 agent」。按下去会：

1. 抓一张**当前整屏截图**
2. 把截图作为**图片附件**贴进一条新消息，投给**用户当前所在的那个对话**
3. 你收到时，消息里有图，也有这段话

截图**不落盘**：它只存在于附件存储和这次消息里。

## 收到呼唤的第一件事

**先读画板，再看图。**

```
pencil scene
```

为什么先读画板：截图告诉你用户在**哪个界面**，但画板告诉你用户**在说什么**。红圈、红箭头、红字都是他在这几秒内留下的具体意图，比截图本身精确得多。

`pencil scene` 返回：

```json
{
  "screen":  { "w": 1920, "h": 1080, "x": 0, "y": 0 },
  "layers":  [ ... 你自己画的 ... ],
  "strokes": [ { "id": "u1-…", "width": 4, "points": [[x,y], …] } ],
  "texts":   [ { "id": "t3-…", "x": 1097, "y": 426, "text": "你的字擦不掉" } ],
  "hidden":  [ ... 已被擦掉的 id ... ]
}
```

- **`screen`** = 这台机器真实的物理分辨率。`unit:"screen"` 的坐标范围就是 `0..w`、`0..h`。**不要假设 1920×1080**，每台机器不同，读这个值。
- `strokes` = 用户的红线，跟 `points` 走一遍就知道他圈了哪块
- `texts` = 用户打的字，**这是他原话**，直接读

### 你看到的图可能和真实桌面不是一个尺寸

呼唤消息里会写明截图尺寸，但那**不一定等于** `screen`：

| 情况 | 例子 |
|---|---|
| 截图是真实尺寸 | 消息说 1920×1080，`screen` 也是 1920×1080 → 直接用 |
| 截图被上游缩过 | 消息说 1536×864，`screen` 是 1920×1080 → **必须申报 `view`** |
| 你自己看图的降采样 | 你内部的视觉表示可能更小 → 按你**实际量到的那张图**的尺寸申报 |

规则只有一条：

```json
pencil { action: "draw", view: { "w": <你量坐标那张图的宽>, "h": <高> }, items: [...] }
```

工具会自动换算，**你不要自己乘 1.25 或除 0.8**。

画完检查返回：

```
rescaled — view 1536x864 mapped to 1920x1080 (x1.2500, y1.2500)
landed at 1375,625 125x100
```

`landed at` 是真实落点，拿它和你想要的位置比。

⚠️ **历史故障（务必记住）**：曾有 agent 拿 1536 的坐标直接画到 1920 画板上，整体缩到 0.8 倍。它发现偏了之后，拿「A 批图元的渲染结果」比「B 批图元的请求坐标」，算出 0.767/0.950 ≈ 0.8，当成「画板被压缩 0.8 倍」的铁证，之后所有修正全建在这个假理论上，越修越远。

**教训**：坐标偏了，先看 `screen` 和 `rescaled`，那是工具给的确定数据；不要用两批不同图元的数据对比去推比例。

## 然后画回去

用户在屏幕上等你。**只在聊天里回复，他可能根本没在看聊天窗。**

所以：

```
pencil draw  { type: "text", x: <他圈的那块附近>, y: …, text: "…", color: "#00E5FF" }
```

- 他圈了控件 → 在控件旁写答案
- 他打了问题 → 在问题下方接着写
- 他画了箭头 → 在箭头终点写

**你的笔迹不用红色**——红是用户的专属色，撞色就分不清谁在说话。

## 定位就用眼睛，别写代码

**这是最容易犯的错，单独说。**

用户让你「圈出某个东西」，你要做的只有一件事：**在图上看到它，估个大概坐标，画框**。

```
看到 → 估坐标 → pencil draw → 完成
```

**百分之几十像素的误差完全没关系。** 用户要的是「你指的是这块」，不是「精确到像素的测量报告」。

### 绝对不要做的事

| ❌ 错误做法 | 为什么是坑 |
|---|---|
| 写 PowerShell 脚本查 SysListView32 图标坐标 | 跨进程读内存经常失败，越试越深 |
| 读注册表 `IconLayouts` 二进制 | 格式没文档，解析起来没完 |
| 做壁纸差分/掩膜检测找图标 | 壁纸一变就废，且要写一堆文件 |
| 写十几个脚本反复试 | **用户看着你写文件只会困惑和烦躁** |

这些错误有一个共同点：**为了「更精确」而绕远路，最后连原本简单的事都没做成，还留下一堆垃圾文件。**

### 为什么这个坑特别诱人

因为「精度」听起来很专业。但用户说「圈出压缩包」时，他要的是一个圈，不是一份测量报告。

**简单直接 > 精确繁琐。**

### 需要看被挡住的桌面时

只有这一种情况需要用工具：桌面被窗口遮住看不全。

装了**钛合金鱼眼**就用：

```
eye { action: "desktop" }
```

它专门为此做的，一行搞定。**不要自己写截图脚本。**

没装就如实告诉用户「桌面被挡住了，请让窗口让开」，别造轮子。

## 什么时候不该画

- 用户在聊天里正常提问，只是顺手按了呼唤 → 直接回聊天，别硬画
- 屏幕上看不出他在指什么 → 先在画板上问一句「你说的是哪块？」，再等他圈

## 边界

- **你不能一键清除画板。** 清空会推翻用户的工作，只有他能做。要删自己的标注就用 `erase`。
- **用户能擦你画的东西。** 他擦掉说明不需要了，不要重画。
- 呼唤是**排队**投递的，不会打断你正在跑的回合。
- **画之前先看 `onScreen`。** 截图能成交付的前提是桌面窗口活着；如果 `onScreen` 是 `false`，说明窗口起不来，这时候画什么都没有用，如实说。

## 窗口没活着怎么办

`pencil` 工具自己会修：每次 `draw` 前检查 `window.txt` 里的 pid，死了就先用指令拉起窗口。插件启用时也会做一次。

所以你正常用就好。唯一要注意的是**别把「文件写成功」当成「用户看到了」**——只有 `onScreen: true` 才算。

真遇到拉不起来：

```
pencil { action: "overlay", overlay: "start" }
```

还是不行就告诉用户窗口起不来，不要假装画好了。
